# DOCX → Markdown（含公式）

把一份满是公式的 Word 文档转成 Markdown，难点**不在**段落和标题——那些是体力活。
真正的难点是公式：Word 的 OLE 公式是一套私有二进制格式，解出来必然失真。

本技能给出经过真实文档验证的流程。核心只有一句话：

> **以渲染出的位图为准，不以解析出的字符为准。**

---

## 一、先认清三种手段的可靠性

| 手段 | 能得到什么 | 可靠性 | 本插件是否提供 |
|---|---|---|---|
| ① 渲染成 PNG 再看图 | 公式的完整视觉 | ★★★★★ | ✅ `docx2md_extract` 产出 `png/` |
| ② 抽 EMF 内嵌的 PDF 文字层 | 视觉一致的字符序列 | ★★★★ | ⚠️ **未实现** |
| ③ 解 MTEF 记录 | 零散字符 | ★★ | ⚠️ 只做变体判定，不产出字符 |

**手段 ② 目前不可用。** 方法论文档里记录过这条路径（作为变体 B 的解法），
但它在那次实验里是手工做的一步，没有固化进本插件。`pypdf` 只在插件依赖里
预留声明，`py/` 下零引用。需要用它时只能自己写，或退回到 ① 读图。

第 ③ 条必须强调，因为它的失败方式最隐蔽——**它不报错，只是给你一个残缺的结果**。
这也是为什么本插件只拿它做变体分类（A 可解 / B 必须看图），**从不拿它当公式来源**。

以下是在一份真实论文（145 个公式）上实测的对比，公式编号是那篇文档里的序号，仅作例证：

| 该篇公式 | 渲染图字符量 | MTEF 解出 | 结果 |
|---|---|---|---|
| #27 | 151 | `βP`（2 字符） | 5 行矩阵式，解出 2 个字符 |
| #30 | 150 | `u=dr`（4 字符） | 5 行，丢 97% |
| #6 | 5 个等式链 | `α=-∇×βP` | 结构全丢 |

**这不是那份文档的特例。** MTEF 记录本身不保存二维排版，只保存一串字符与位置提示，
所以任何多行结构（矩阵、分段函数、多行推导）都无法从中还原。

所以：**渲染失败就停下并报告，不要降级去解 MTEF。** 一个明确说"这几个公式我没转出来"
的结果，比一个看起来完整实则错误的文档有价值得多。

## 二、标准流程

```
docx2md_inspect   →  看清有什么、能不能转
docx2md_extract   →  正文 + 公式索引 + 预览图（渲染成 PNG）
【人工/视觉】      →  逐张读 PNG，转写成 LaTeX   ← 唯一不可自动化的一步
docx2md_build     →  合成为 Markdown 并校验
```

### 第 0 步：转换前先问清楚

- **旧 .doc 必须先存成 .docx**（用 Word 或 WPS 打开另存）。本工具链只吃 .docx。
- 如果文档里有**插图**，问用户要图片文件，或先单独抽出来。不要把公式里的希腊字母
  当数据，也不要把插图漏掉。

### 第 1 步：inspect

```
docx2md_inspect(path="文档.docx")
```

看三件事：
- `formulas` —— 一共有多少公式，决定读图的工作量
- `variants` —— A 可解字符 / B 不可解；B 多说明必须走渲染
- `render_engines.can_render` —— 本机能不能渲染。false 就先解决这个

### 第 2 步：extract

```
docx2md_extract(path="文档.docx", outDir="work/")
```

产出：
- `paras.json` —— 正文段落，公式位置是 `⟦EQ:oleObject12.bin⟧` 占位
- `eq_index.json` —— 每个公式的 stream 名、预览图、字节数、变体、`pairing`
- `media/` —— 原始矢量图（EMF/WMF）
- `png/` —— 可读位图（**读这个目录**）

**读图前先看 `summary.json` 的两个字段，它们决定这些图能不能信：**

| 字段 | 含义 | 该怎么办 |
|---|---|---|
| `formulas_paired_by_shape_id` | 按 `o:ole="t"` 的 shape 精确配到的公式数 | 这是可信的，直接读 |
| `formulas_paired_by_ordinal` | 找不到 ShapeID、退回「同段落第 k 个公式配第 k 张图」的数量 | **不可信**，见下 |

`pairing` 字段写在 `eq_index.json` 每一条里（`shape-id` / `ordinal` / `none`）。
出现 `ordinal` 时，说明文档没写 `ShapeID`，那张图可能是**同段落里插图的位图**
而不是公式——插件无法区分，只会如实告诉你它不确定。这种公式要么放大核对图里
到底是不是公式，要么回原 Word 看。`none` 则是真的没有预览图。

> 这条不是洁癖：早期版本一律按顺序配对，在公式前面夹着插图的段落里整体错位，
> 实测一份 145 公式的文档错了 10 个，而且**没有任何提示**——模型会把程序截图
> 读成"公式"，产出一个看起来完整、实则全错的结果。

### 第 3 步：读图转写 LaTeX（核心）

**逐张读 `png/` 里的图**，把每条公式抄成 LaTeX，写成一张映射表：

```json
{
  "oleObject1.bin": "\\alpha",
  "oleObject4.bin": "\\boldsymbol{\\beta}^{P}=\\nabla\\mathbf{u}^{P}"
}
```

键就是 `eq_index.json` 里的 `stream`。

几条实践经验：

1. **一次读一批，别一次读一张。** 用文件列表批量读，效率高得多。
2. **不要凭印象补。** 看不清就放大，或者换 ② 路径交叉验证。宁可标 TODO 也不要猜。
3. **注意张量约定。** 并矢的指标顺序（`α = Σ ρ_b b` 的线方向在前还是后）是
   作者的约定，不是错误。照抄，不要"纠正"。
4. **矩阵/多行公式最容易出错。** 数清楚有几行、每行的层级。这类公式通常正是
   变体 B，必须靠看图。

### 第 4 步：build

先出标题初稿，人工过一遍：

```
docx2md_build(workDir="work/", latex="latex.json", out="文档.md",
              suggestHeadings=true)
```

读 `work/headings_suggested.json`。**中文文档的标题层级几乎不可能全自动识别**——
`1．`、`A）`、`i）`、以及无编号的「引言」混用是常态。改好后存为 `headings.json`，
再正式构建：

```
docx2md_build(workDir="work/", latex="latex.json", out="文档.md",
              expectFormulas=<inspect 报出的 formulas 值>)
```

`expectFormulas` 会校验公式总数，能抓住"漏了几个公式"这类问题。

**校验器还会查未解析的公式（T9）**：latex 表里缺的公式，build 会写成
`<!-- 未解析公式: oleObject7.bin -->`。这种文档结构完全合规、六条铁律全过，
注释渲染后也看不见，但正文里就是少了公式 —— 所以校验器把它判为 FAIL。
看到 `T9` 就说明你的 latex 表漏了公式，补上再构建，不要靠调低校验强度绕过。

构建成功后可以用 `cleanup=true` 删掉 `media/`、`png/`。校验没通过时不会删，
方便你回头核对是哪张图读错了。

### 排版阈值：什么时候该调

两个阈值决定「公式是留在句子里，还是独立成块」。它们有默认值，但**没有唯一
正确值**——取决于这篇文档给谁看。

| 参数 | 默认 | 作用 | 调大的后果 |
|---|---|---|---|
| `longTexChars` | 80 | 混排段里，LaTeX 源串超过这个长度就独立成块 | 更多公式留在句内、句子更连贯；但长式在中文字里会折行、窄栏里可能溢出 |
| `t5MaxCellFormula` | 60 | 表格单元格内公式的字符上限，超过则给 T5 警告 | 更多长式允许留在表格里（T5 只是警告，不影响 PASS） |

同一篇文档（145 个公式）实测的取舍：

| `longTexChars` | 行内 | 独立成块 |
|---|---|---|
| 40 | 28 | 117 |
| 80（默认） | 43 | 102 |
| 150 | 57 | 88 |
| 300 | 68 | 77 |

公式总数始终是 145，改编排不会丢公式。

**什么时候调小**：文档要在移动端 / 窄栏显示，或用户反馈「公式把句子撑破了」。
**什么时候调大**：用户更在意句子连贯，且渲染环境较宽（桌面、A4 单栏）。

两种传法，优先级是「单次调用 > 插件配置」：

```
# 只对这一篇调，不改全局
docx2md_build(workDir="work/", latex="latex.json", out="文档.md", longTexChars=150)
```

改全局默认则写 profile 的 `cordis.patch.yml`（**不是**插件管理界面，那里没有
参数表单）：

```yaml
- id: docx2md
  name: dsh-docx2md
  config:
    longTexChars: 150
    t5MaxCellFormula: 200
```

`build` 的返回值里会回报 `long_tex_chars`，用它确认参数真的生效了——
不要只看自己传了什么。配置写错时不会报错，只会静默用默认值。

## 三、六条铁律（每条都真实踩过）

### 1. `$$` 必须独占一行

```
差：$$E = mc^2$$           ← 有些渲染器不认
好：
$$
E = mc^2
$$
```

**这是最危险的一条。** 写成 `$$\begin{aligned}` 时，它不被识别为块级公式，
于是和后面某个 `$$` 错误配对，**从那里到文末全部错乱**。而且不会有任何报错。

### 2. 行内公式不能跨行

`$...$` 里不能出现 `\begin{aligned}`、`\\`、`&`。多行结构一律用 `$$` 块。

### 3. 相邻公式之间要隔开

`$a$$b$` 会被解析成一个 `$$` 定界符。两个公式之间必须有空行、或普通文字。

### 4. `\tag` 紧跟 `\end{aligned}`

```
$$
\begin{aligned}
...
\end{aligned}\tag{12}
$$
```

### 5. 超长公式不要塞进表格

表格单元格里的长公式几乎必然渲染失败。超过约 60 字符就移出表格。

### 6. 图片占位用 HTML 注释

```markdown
<!-- 图 1：位错环与曲面 S -->
```

用户后面会替换成真图。用 `![]()` 空链接会在不少渲染器里显示成破图。

## 四、编号管理

公式编号最容易出错，因为**"删除一个编号再全局重排"会把删掉的又加回来**。

正确顺序：

1. 先把所有 `\tag{...}` 清空
2. 给**不参与编号**的公式区域打上哨兵标记（如 `@@NOEQ@@`…`@@END@@`）
3. 分段编号，跳过哨兵区域
4. 去掉哨兵

永远不要"改一个补一个"。整篇重排一次，比局部修补可靠。

## 五、内容保真的自查

转换完成后，**一定要做一次内容对照**：

```bash
# 去掉空白和标点后比对字符数
python - <<'EOF'
import re
a = open('原文备份.md').read()
b = open('转换结果.md').read()
norm = lambda s: re.sub(r'\s+', '', s)
print(len(norm(a)), len(norm(b)))
EOF
```

字符数应当接近（公式改写会导致差异，但正文不该大幅变动）。

**真实教训**：一次表格化改造中，正则要求"标签后有 2 个空格"，而某一行只有 1 个，
于是那一整句「单位体积受到的力场」被静默丢弃。是靠这个比对发现的。

另外注意：**不要顺手改原文措辞**。删一个多余的「因此」、把「4」改成「四」、
把句号改成分号——这些都会被视为篡改。只做格式转换，内容一字不动。

## 六、不要自己画示意图

用户提供的示意图（位错环、曲面、法向、dS、dℓ 那类）包含大量视觉约定：
线型、粗细、虚实、点的位置、标注的相对关系。

**用文字描述重画它，几乎一定失败。** 实测 7 轮重画，每次都漏掉"中间那条点划线"
或把"两端尖的梭形"画成"扁椭圆"，最后用户放弃。

正确做法：在 Markdown 里留 HTML 注释占位，**向用户要原图文件**。

## 七、典型失败的信号

转换中如果出现下面任何一条，停下来检查：

| 信号 | 大概率原因 |
|---|---|
| 某个公式之后的内容全部变成纯文本 | `$$` 配对错位（铁律 1/3） |
| 公式显示成 `\begin{aligned}` 原文 | 写在行内公式里了（铁律 2） |
| **公式显示成 LaTeX 源码，或整块空白** | **`$` 与中文紧贴，渲染器没识别成公式（T10）** |
| 只有长公式、矩阵坏，短的正常 | 同上，或行内公式里塞了块级环境（T2） |
| 图片显示成破图 | 用了空 `![]()`（铁律 6） |
| 公式数量比预期少 | 占位符没被替换，或原文本身漏了 |
| 段落里出现孤立的 `，` 或 `。` | 公式被拆成块后，标点留在了外面 |
| 编号重复或跳号 | 局部修补了编号（见第四节） |
| 读出的"公式"其实是截图/示意图 | `summary.formulas_paired_by_ordinal > 0`：那张图是退回顺序配对配上的，未经确认（见第 2 步） |
| 中文变成 `����`，或出现 U+FFFD | Python 输出编码不是 UTF-8。正常情况下插件已在进程层与脚本层各夹一道（`pyEnv()` + `force_utf8_stdio()`）；若仍出现，说明有人绕过插件直接跑了 `py/*.py`，或用了改过的解释器 —— 先跑 `node test/encoding.mjs` 定位 |

### 公式显示不出来，先查这三件事

`docx2md_build` 只保证 Markdown 结构合规，**不保证每个渲染器都认**。按命中率排序：

1. **`$` 与中文紧贴**（最常见）。`中文$公式$中文` 在 Pandoc、部分 KaTeX 集成里
   会被当成普通文本。写成 `中文 $公式$ 中文`。校验器的 **T10** 会逐处报出来。
2. **行内公式里有块级环境**。`$...$` 里出现 `\begin{aligned}`、`\\`、`&` 一定坏，
   必须改成 `$$` 块（**T2** 会报）。
3. **渲染器本身不认 `$` 语法**。有些 Markdown 预览器默认只认 `\(...\)` 或
   ```math 代码块。这种情况换渲染器验证一次即可确认：语法没问题、只是预览器
   的配置问题。

> 一条实测经验：`kaTeX.renderToString` 能渲染，**不等于** Markdown 解析器会把它
> 识别成公式。这是两层独立的判定，必须分开测。只测前者会给你虚假的信心。

> 判据：`missing_preview_context[].paragraph_text` 必须能读出汉字。这是判断
> 「缺图公式是图注还是正文」的唯一依据；它是乱码时不要凭猜测定性，先修编码。
